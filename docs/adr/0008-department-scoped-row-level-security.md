# ADR-0008: Row-Level Security в разрезе департаментов

- Статус: Принято
- Дата: 2026-06-29
- Решение принял: Vlad (Softwarean)

## Контекст

Центральный риск многодепартаментной RAG-системы — утечка между
департаментами: поиск выдаёт фрагмент, который спрашивающему видеть не
положено. Если изоляция держится только на коде приложения, одного забытого
`WHERE` в любом пути поиска хватает для утечки, и база данных уже ничем не
поможет.

## Решение

Обеспечивать изоляцию департаментов в PostgreSQL через Row-Level Security.
Каждая таблица в разрезе департамента несёт `department_id`. Политики опираются
на транзакционную переменную сессии (`app.current_user_id`) и функцию проверки
членства. RLS включён в режиме `FORCE`, так что владельцу таблицы политики тоже
предъявляются; приложение подключается ролью `app_user` без прав суперпользователя;
политики закрываются по умолчанию (ноль строк), когда переменная сессии не
установлена.

## Рассмотренные альтернативы

- **Фильтрация только на уровне приложения** — это не эшелонированная защита:
  одна ошибка выпускает всё, и у базы нет страховочного слоя. Отклонено.
- **Отдельная схема или база на департамент** — тяжело, усложняет общие
  справочники и межведомственное администрирование, болезненно мигрируется.
  Отклонено.
- **Отдельная роль Postgres на департамент** — взрывной рост числа ролей, и
  модель плохо ложится на пользователя, состоящего сразу в нескольких
  департаментах. Отклонено.

## Последствия

**Плюсы**
- База — последний рубеж обороны: даже ошибочный поисковый запрос не вернёт
  строки вне департаментов пользователя.
- Аудит и журнал происхождения ответов не страдают и находятся за той же
  границей.

**Издержки**
- Политики нужно писать и тестировать аккуратно.
- Приложение никогда не должно подключаться суперпользователем или ролью с
  `BYPASSRLS` — иначе RLS молча перестаёт что-либо делать.
- Переменная сессии обязана быть транзакционной (`set_config(..., true)`) при
  работе через пул соединений, иначе личность одного запроса протечёт в
  следующий.

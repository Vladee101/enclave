# ADR-0018: Минимальные привилегии роли app_user

- Статус: Принято
- Дата: 2026-09-23
- Решение принял: Vlad (Softwarean)

## Контекст

ADR-0008 делает базу границей безопасности: изоляцию держат политики RLS, а не
код приложения. ADR-0015–0017 продолжили эту линию — удаление документов и
департаментов проверяет функция в базе, а не команда. Всё это опирается на
одно допущение: роль `app_user`, под которой идут пользовательские запросы,
не может менять то, на чём держатся проверки.

Допущение не выполнялось. При закрытии мелкой проблемы — любой член
департамента мог переписать назначения LoRA-адаптеров своего департамента —
сверка привилегий показала общую картину:

- `004_rls.sql` выдала `app_user` `SELECT, INSERT, UPDATE, DELETE` на все
  свои таблицы. Там, где у таблицы нет RLS или нет политики на запись, это
  право работало напрямую.
- **`users` без RLS.** Проверено на живой базе в откатываемой транзакции:
  `UPDATE users SET is_admin = true` под `app_user` проходит. Это прямая
  эскалация до администратора — мимо проверок в `delete_document()` и
  `delete_department()`, которые доверяют `users.is_admin`. Воспроизводится
  на чистой базе из миграций 001–011, не только на дрейфнувшей dev-базе.
- `embedding_models`, `adapters` без RLS — `app_user` мог регистрировать
  модели эмбеддингов и файлы адаптеров; `department_adapters` — политики на
  запись для любого члена департамента.
- В базах, куда когда-то вручную применяли `db/schema.sql`, — права на запись
  даже в `_sqlx_migrations` и **привилегии по умолчанию**: каждая новая таблица
  в `public` автоматически давала `app_user` запись, каждая новая функция —
  `EXECUTE`. Любая следующая миграция открыла бы то же заново.

Из интерфейса это недостижимо: webview не выполняет SQL, запросы в ядре
фиксированы. Но модель «граница — база» обещает ровно обратное: ошибка в коде
(например, SQL-инъекция) не должна давать больше, чем даёт роль.

## Решение

`app_user` пишет ровно то, что пишет приложение через `app_pool`, и больше
ничего:

| Таблица          | Запись                                             |
|------------------|----------------------------------------------------|
| `documents`      | `INSERT` (загрузка), `UPDATE` только `status`, `updated_at` (повторная постановка) |
| `ingestion_jobs` | `INSERT` (загрузка)                                |
| `audit_log`      | `INSERT` (только свои строки — политика `audit_log_own_insert`) |

Всё остальное — только чтение (и то под RLS, где она есть). Привилегированные
действия идут через `admin_pool` (провижининг) или через функции
`SECURITY DEFINER` с собственной проверкой (удаление).

Миграция 012:

- отзывает у `app_user` все права на запись на **все** таблицы схемы, включая
  спящие таблицы из `schema.sql` и `_sqlx_migrations`, и выдаёт обратно три
  строки из таблицы выше;
- удаляет политики на запись, которые больше нечему применять
  (`adapters_dept_insert/update/delete`, `ingestion_jobs_dept_update`), чтобы
  они не ожили при случайной повторной выдаче права;
- снимает привилегии по умолчанию на запись и `EXECUTE` — по каждой роли-
  владельцу и по каждой схеме (в дрейфнувших базах они заданы
  `IN SCHEMA public`, и глобальный отзыв их не трогает). Чтение новых таблиц
  остаётся автоматическим.

## Рассмотренные альтернативы

- **Включить RLS на `users`, `embedding_models`, `adapters`** и писать политики.
  Политика «пользователь меняет только свою строку» всё равно пропустила бы
  `UPDATE users SET is_admin = true` для собственной строки — нужно было бы
  ещё и ограничение по колонкам. Привилегии решают задачу прямо: у роли нет
  права писать — нечего и фильтровать. Отклонено как основной механизм.
- **Закрыть только найденное** (`users`, `department_adapters`). Оставляет
  дрейф привилегий по умолчанию, который откроет следующую таблицу. Отклонено.
- **Отдельная роль на каждую команду.** Точнее, но умножает пулы и строки
  подключения ради выигрыша, который уже даёт таблица выше. Отклонено.

## Последствия

- Любая новая запись через `app_pool` требует явного `GRANT` в миграции рядом
  с кодом, который пишет. Привилегии по умолчанию больше этого не сделают —
  это намеренное трение.
- `rls_validation` (раздел 9) проверяет двенадцать запрещённых записей — от
  `UPDATE users SET is_admin` до записи в таблицу, созданную после миграций, —
  и то, что три разрешённые продолжают работать. Перед миграциями тест
  воспроизводит дрейф привилегий по умолчанию, иначе проверка «таблица,
  созданная позже» на чистой базе проходила бы тривиально. Без миграции 012
  тест падает на эскалации (проверено).
- Административные команды по-прежнему идут через пул суперпользователя
  (`admin_pool`); перевод их на функции с проверкой в базе, как у удаления, —
  кандидат на отдельное решение.

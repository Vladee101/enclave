# ADR-0021: Политики RLS вычисляют членство один раз на запрос; спящие политики удалены

- Статус: Принято
- Дата: 2026-09-24
- Решение принял: Vlad (Softwarean)
- Замещает: ADR-0011

## Контекст

Поиск по таблице из 50 000 строк (ADR-0020) занимал 1,3–2,2 секунды. План
запроса показал, что время уходит не на поиск:

| Поиск одного слова по 50 000 фрагментам департамента | Время |
|---|---|
| с действующими политиками | 257 мс |
| без политик, только сопоставление текста | 20 мс |
| сопоставление + проверка членства по готовому массиву | 15 мс |
| GIN-индекс (без RLS) | 0,08 мс |

Две причины:

1. Политики вида `is_member_of(department_id)` выполняли подзапрос к
   `department_members` **на каждой строке**.
2. В базах, где когда-то вручную применяли `db/schema.sql`, рядом работали
   **спящие** политики на `app_user_in_department(department_id)` (ADR-0011) —
   и тоже на каждой строке. Разрешающие политики объединяются по OR, так что
   Postgres вычислял обе.

GIN-индекс под RLS не помогает вовсе: оператор `@@` не помечен leakproof, и
планировщик не вправе применить его раньше политики. Значит, поиск
неизбежно проходит по фрагментам департамента — и стоимость политики на строку
решает всё.

ADR-0011 откладывал удаление спящих политик до появления проверки, что после
удаления каждый видит ровно то же. Такая проверка теперь есть:
`rls_validation` (девять разделов) в CI на каждый push.

## Решение

**Форма политик.** Функция `current_user_department_ids()` (`SECURITY DEFINER`,
`STABLE`) возвращает массив департаментов текущего пользователя; политики
сравнивают строку с ним:

```sql
department_id = ANY ((SELECT current_user_department_ids())::uuid[])
```

Обёртка `(SELECT …)` превращает вызов в InitPlan — одно вычисление на запрос;
приведение `::uuid[]` нужно, иначе `ANY ((SELECT …))` читается как «любая строка
подзапроса» и сравнивает `uuid` с `uuid[]`. Смысл политик не меняется: строка
видна членам её департамента, решает база. Меняется только цена проверки.
Пустая личность даёт пустой массив — ноль строк, как и раньше.

**Спящие политики удалены.** Миграция 013 находит их не по именам (они
различаются между базами), а по вызываемым функциям `app_user_in_department` /
`app_current_user_id`, удаляет, затем удаляет сами функции. Неиспользуемые
таблицы из `schema.sql` (`conversations`, `messages`, `query_logs`,
`memberships` …) остаются с включённым RLS без политик, то есть под `FORCE`
закрыты полностью.

## Проверка

- `rls_validation` — все девять разделов на чистой базе с новой формой политик.
- На дрейфнувшей dev-базе (с 12 спящими политиками) до и после миграции снят
  отпечаток видимого каждому пользователю: число строк и хэш их id по восьми
  таблицам для четырёх пользователей. Отпечатки совпали полностью — план
  ADR-0011 («убедиться, что политики дают те же результаты») выполнен.
- Поиск по 50 000 строкам: 2,2 → 0,22 с.

## Рассмотренные альтернативы

- **Пометить `ts_match_vq` (`@@`) как LEAKPROOF,** чтобы под RLS работал
  GIN-индекс. Это правка системного каталога суперпользователем, которая не
  переживает обновление Postgres и утверждает свойство функции, которое её
  авторы не заявляли. Отклонено.
- **Функция поиска `SECURITY DEFINER` в обход RLS** с явным фильтром по
  департаментам. Быстрее (индекс), но переносит границу изоляции для основного
  пути чтения из политик в код функции — против ADR-0008. Отклонено; вернуться,
  если объёмы переживут и эту оптимизацию.
- **Удалять спящие политики по одной таблице** (план ADR-0011). Нужен был,
  пока не было автоматической проверки; с `rls_validation` в CI и сравнением
  отпечатков видимости одна миграция безопаснее цепочки. Отклонено.

## Последствия

- Любая новая политика на таблице в разрезе департамента пишется в той же
  форме — `= ANY ((SELECT current_user_department_ids())::uuid[])`, никогда не
  функцией от строки (инвариант в CLAUDE.md).
- Поиск остаётся линейным по числу фрагментов департамента пользователя
  (≈ 15 мс на слово на 50 000 фрагментов). На сотнях тысяч фрагментов на
  департамент понадобится решение из «Альтернатив».
- `is_member_of()` остаётся — ею пользуются `delete_document()` и
  `delete_department()`, где проверяется одна строка.

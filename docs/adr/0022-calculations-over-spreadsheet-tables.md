# ADR-0022: Расчёты по таблицам: план от модели, SQL от ядра

- Статус: Принято
- Дата: 2026-09-24
- Решение принял: Vlad (Softwarean)

## Контекст

ADR-0020 научил приём таблиц. Строка таблицы превращается в самостоятельный
фрагмент, и RAG отвечает на вопросы о конкретной строке («какая сумма у
договора Д-012345»). Считать RAG не умеет: «сколько договоров заключено в
2021 году» или «общая сумма договоров Петровой» не содержатся ни в одном
фрагменте. Модель видит 5 строк из 50 000 и может разве что сделать вид, что
посчитала. А в корпоративных таблицах такие вопросы задают чаще всего.

Прямой путь (text-to-SQL, модель пишет запрос) здесь не подходит по двум
причинам:

1. **Безопасность.** Запрос, написанный моделью, — это произвольный SQL по
   вводу пользователя и по содержимому документов. Выполнить его на
   `app_pool` значит разрешить модели всё, что разрешено `app_user`. RLS
   закрыла бы чужие строки (ADR-0008), но не остальные ошибки: тяжёлые
   запросы, обращения к служебным таблицам, изменение контекста сессии.
2. **Качество.** Модель на 3B параметров пишет SQL по схеме с JSONB-ячейками
   ненадёжно. Проверить такой запрос, не выполняя его, нельзя.

## Решение

**Таблицы хранятся ещё и как таблицы.** При приёме каждый лист, кроме текста
для RAG, записывается в `sheet_tables` (столбцы с выведенным типом и
статистикой) и `sheet_rows` (строки как JSONB-массивы). Запись идёт в той же
транзакции воркера, что и фрагменты. Документ становится `ready` с тем и
другим или ни с чем. `department_id` проставляет воркер (ADR-0009). Для
`app_user` обе таблицы доступны только на чтение, политики RLS пишутся в
форме «один раз на запрос» (ADR-0021). При удалении документа таблицы
удаляет триггер на `documents.deleted_at`. Оба пути удаления
(`delete_document()`, `delete_department()`) ставят надгробие именно там.

**Типы столбцов** определяются по большинству ячеек: число или дата, если
так выглядят не меньше 90 % заполненных ячеек. Одно «н/д» в столбце сумм не
превращает его в текст. Числа, набранные текстом по-русски («120 000,50»), и
даты вида `15.03.2021` распознаются. Числа пишутся в JSONB так, как их
показывает ячейка (`0.3`, а не `0.30000000000000004`). Postgres читает их как
`numeric`, и суммы получаются точными десятичными. Для текстовых столбцов
хранятся до 30 самых частых значений. Если это все значения столбца, столбец
считается **закрытым**.

**Модель строит план, а не SQL.** Путь вопроса:

1. Обычный гибридный поиск под RLS. Если среди найденных документов есть
   таблицы, они становятся кандидатами (до трёх). Таблицу выбирает поиск, и
   модели не нужно видеть весь каталог.
2. Модель получает описание кандидатов: столбцы, типы, частые значения,
   диапазоны. Ответ ограничен **JSON-схемой, собранной из этих самых
   столбцов**. llama-server превращает её в грамматику, и модель физически не
   может назвать несуществующий столбец, применить `sum` к тексту или (для
   закрытого столбца) написать значение, которого нет в таблице. План
   состоит из метрики (count / sum / avg / min / max), группировки (столбец,
   для дат — год, месяц или день), фильтров (до четырёх) и порядка. Модель
   может ответить и «не расчёт» (`{"answerable": false}`).
3. Ядро проверяет план по каталогу и компилирует его в один агрегатный
   запрос по `sheet_rows`. Номера столбцов и значения передаются
   **параметрами**, а текст SQL собирается только из фиксированных
   фрагментов. Запрос выполняется на `app_pool` с установленной личностью,
   так что RLS решает, какие строки существуют.
4. Модель пересказывает готовые числа («не пересчитывай, не округляй»).
   Пользователь видит под ответом блок «How this was calculated»: файл,
   лист, условия, число подошедших строк, результат.

**Отказ — это обычный RAG, а не приблизительное число.** Если модель сказала
«не расчёт», план не прошёл проверку или запрос упал (он выполняется в
savepoint), вопрос отвечается как раньше, по фрагментам. Вопросы о конкретной
записи модель направляет туда же: поиск находит строку лучше, чем фильтр.

**Аудит.** Для расчёта в `audit_log` пишутся документ, таблица и число
подошедших строк (идентификаторы, без текста вопроса — как для RAG).

## Проверка на живой модели (Qwen 2.5 3B, реестр 2 000 строк)

Все числа сверены с прямым SQL по той же базе.

| Вопрос | План модели | Результат |
|---|---|---|
| Какая общая сумма договоров Петровой А.С.? | sum, «Ответственный» содержит «Петрова А.С.» | 1 195 540 750 — верно |
| Сколько договоров было заключено в 2021 году? | count, дата ≥ 2021-01-01, ≤ 2021-12-31 | 400 — верно |
| Сколько договоров по каждому статусу? | count по «Статус» | 667 / 667 / 666 — верно |
| Сколько договоров заключено по годам? | count по году «Дата заключения» | по 400 за 2020–2024 — верно |
| Какой средний размер договора в отделе Логистика? | avg, «Отдел» содержит «Логистика» | 2 390 040.75 — верно |
| Сколько действующих договоров у Кузнецовой в 2023 году? | count, три фильтра | 34 — верно |
| Когда был заключён самый ранний договор отдела ИТ? | min даты, фильтр по отделу | 2024-01-01 — верно |
| Какая сумма у договора Д-001234? | «не расчёт» → RAG | 4 772 046 — верно, с цитатой |
| Что является предметом договоров? | «не расчёт» → RAG | верно |

**На реестре из 50 000 строк** (тот же файл, что в ADR-0020) шесть вопросов
дали верные числа, сверенные с SQL: сумма по ответственному (12 500 строк,
31 188 518 750), число за год (10 000), по статусам, среднее по отделам,
пересечение трёх условий (833), сумма договора по номеру. Сам агрегат под RLS
выполняется за 21 мс (`EXPLAIN ANALYZE` от `app_user`). Подготовка ответа
занимает 1,3–3,1 с, почти всё это время уходит на вызов планировщика. Запись
табличного представления 50 000 строк при приёме занимает 0,5 с.

Первая версия справлялась с 1 из 4 вопросов. Модель искажала имена
(«Петров А.С.» — ноль строк), добавляла фильтры, которых в вопросе нет, и
выбирала не ту метрику. Помогли три вещи:

- перечень значений для закрытых столбцов в грамматике;
- порядок полей: сначала метрика, потом фильтры. `serde_json` по умолчанию
  сортирует ключи, и модель писала `filters` раньше `metric`; включён
  `preserve_order`;
- семь примеров «вопрос → план» в промпте.

Отдельная поправка: два разных `=` по одному числовому столбцу или столбцу
дат (`= 2021-01-01` и `= 2021-12-31`) не совпадают ни с одной строкой. Модель
так пишет «в течение 2021 года», поэтому пара читается как диапазон.

## Рассмотренные альтернативы

- **Text-to-SQL с проверкой запроса** (парсер SQL, белый список функций,
  read-only транзакция, отдельная роль). Проверка произвольного SQL — это
  собственный анализатор запросов, и каждая его дыра становится дырой
  безопасности. Качество SQL от модели на 3B хуже качества плана. Отклонено.
- **Отдельная таблица Postgres на каждый лист** (`CREATE TABLE` при приёме,
  настоящие типизированные столбцы). Быстрее JSONB, но DDL из воркера,
  политики RLS на каждую таблицу и права на динамически созданные объекты —
  против ADR-0018. Отклонено; вернуться, если JSONB станет узким местом.
- **Считать в Rust по строкам, выгруженным в память.** Те же данные, но
  без RLS на уровне строк при расчёте и с передачей 50 000 строк на каждый
  вопрос. Отклонено.
- **Правила на ключевых словах** («сколько» → count) вместо модели.
  Ломаются на первой же перефразировке и не выбирают столбец. Отклонено.
- **Вызывать планировщик на каждый вопрос.** Лишние ~1 с там, где таблиц нет
  вовсе. Планировщик вызывается, только если поиск нашёл строки таблицы.

## Последствия

- Вопрос по таблице стоит на один вызов модели больше: ~1–2 с на подготовку
  против ~0,2 с у RAG (RTX 4050).
- **Модель может неверно понять вопрос, но не может неверно посчитать.**
  «Самая большая сумма расторгнутых договоров у кого» она поняла как
  максимум одного договора, а не сумму по ответственному. Поэтому расчёт
  всегда показывается пользователю: видно, что именно посчитано.
- Поддерживается одна метрика и одна группировка на вопрос, без соединения
  таблиц, без вычисляемых выражений («сумма минус НДС») и без процентов от
  итога. Групп показывается до десяти, остальные называются числом.
- Таблицы, загруженные до миграции 014, не имеют табличного представления.
  Их нужно загрузить заново.
- Инвариант CLAUDE.md: SQL расчёта собирается только из фиксированных
  фрагментов, все значения — параметры. План модели — это данные, а не код.
- Тесты: `tables` (типы, разбор чисел и дат, схема, проверка планов,
  параметризация), `tests/table_aggregation.rs` (точные суммы, группы,
  диапазоны дат, изоляция под RLS, удаление вместе с документом — падает без
  политики и без триггера, проверено), `rls_validation` раздел 9 (`app_user`
  не пишет в `sheet_*`).

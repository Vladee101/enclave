# ADR-0007: Отдельная таблица эмбеддингов и реестр моделей

- Статус: Принято
- Дата: 2026-06-29
- Решение принял: Vlad (Softwarean)

## Контекст

Эмбеддинг фрагмента — функция от самого фрагмента *и* от модели, которая его
посчитала. Модели эмбеддингов улучшаются, и пересчёт корпуса более сильной
моделью — реалистичная будущая потребность. Схема хранения не должна делать это
разрушительной операцией и при этом обязана поддерживать пригодный ANN-индекс.

## Решение

Хранить векторы в таблице `chunk_embeddings` с ключом
`(chunk_id, embedding_model_id)` и реестром `embedding_models`, где записаны имя
и размерность каждой модели. Колонку вектора зафиксировать по размерности (768,
класс nomic-embed-text / bge-base), чтобы был возможен один общий HNSW-индекс.

## Рассмотренные альтернативы

- **Колонка-вектор прямо в `chunks`** — пересчёт превращается в разрушительную
  перезапись, и нельзя держать векторы двух моделей одновременно. Отклонено.
- **Колонка `vector` без фиксированной размерности** — тогда единый HNSW-индекс
  построить нельзя, понадобится по частичному индексу на модель. Это
  задокументированный запасной выход, если когда-нибудь потребуется несколько
  размерностей сразу, но не вариант по умолчанию. Отклонено пока что.

## Последствия

**Плюсы**
- Пересчёт новой моделью — аддитивная, а не разрушительная операция.
- Ясное происхождение: каждый вектор знает, какая модель его произвела.

**Издержки**
- Фиксированная размерность допускает только одну размерность на общий индекс
  (смягчение — частичный индекс на модель, см. выше).
- Поиск платит один дополнительный индексный join из `chunks` в
  `chunk_embeddings`. Приемлемо.

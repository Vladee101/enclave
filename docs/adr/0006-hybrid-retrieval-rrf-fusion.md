# ADR-0006: Гибридный поиск со слиянием по RRF

- Статус: Принято
- Дата: 2026-06-29
- Решение принял: Vlad (Softwarean)

## Контекст

Плотный векторный поиск ловит смысловое сходство, но спотыкается на точных
токенах — артикулах, фамилиях, аббревиатурах, кодах ошибок, — которые в
корпоративных документах несут много смысла. Лексический полнотекстовый поиск
берёт такие термины точно, но промахивается на перефразировках и синонимах.
Каждый по отдельности оставляет целый класс запросов плохо обслуженным.

## Решение

Выполнять оба поиска и сливать результаты. Плотная ветка — косинусный ANN
pgvector по `chunk_embeddings`; лексическая — полнотекстовый `tsvector` Postgres
по `chunks.content_tsv`. Два ранжированных списка объединяются в ядре на Rust
методом Reciprocal Rank Fusion.

## Рассмотренные альтернативы

- **Только плотный поиск** — проваливается на точных идентификаторах, а они в
  этой области часты и важны. Отклонено.
- **Только лексический** — нет смыслового охвата, теряются релевантные
  фрагменты без общих поверхностных слов. Отклонено.
- **Взвешенная смесь сырых оценок** — косинусное расстояние и полнотекстовый
  ранг лежат на несопоставимых шкалах, поэтому смесь требует хрупкой
  нормализации и подстройки. RRF работает по рангам, и ничего этого ему не
  нужно. Отклонено.

## Последствия

**Плюсы**
- Устойчивость к разным типам запросов: от «найди пункт про X» до «документ
  4471-B».
- RRF прост и по сути не имеет настраиваемых параметров.

**Издержки**
- Два индекса в обслуживании: HNSW по эмбеддингу и GIN по tsvector.
- Небольшая логика слияния живёт в приложении, а не в запросе.

# ADR-0026: Резервная копия — один архив с базой и файлами; восстановление подменяет данные при следующем запуске

- Статус: Принято
- Дата: 2026-09-27
- Решение принял: Vlad (Softwarean)

## Контекст

Со встроенным PostgreSQL (ADR-0014) все данные организации лежат в профиле
одного пользователя Windows: `pgdata` и хранилище файлов `blobs`
(контентно-адресуемое, `{sha256}`). Если сломается диск или переустановят
систему, пропадут и документы, и департаменты, и журнал аудита. Сделать копию
вручную нельзя: база в работе, пароли ролей зашифрованы DPAPI, и обычный
пользователь не знает, где всё лежит.

Есть и второй повод. Данные разработки живут в Docker-базе, а установленное
приложение работает со своей. Нужен штатный путь, чтобы перенести данные из
одной в другую.

## Решение

**Администратор на странице Admin сохраняет копию в один файл
`.enclave-backup` и восстанавливает из него** (`backup.rs`,
`commands/backup.rs`).

### Архив

Формат — ZIP. Все записи хранятся без сжатия: дамп уже сжат самим pg_dump,
а PDF, DOCX и XLSX сжаты своими форматами.

| Запись | Что это |
|---|---|
| `enclave-backup.json` | Опись: версия формата и приложения, время, номер последней миграции, счётчики для подтверждения, размер и SHA-256 остальных записей |
| `database.dump` | `pg_dump --format=custom` всей базы |
| `blobs/{sha256}` | Файл каждого живого документа |

- **Один снимок.** Транзакция REPEATABLE READ экспортирует снимок
  (`pg_export_snapshot`). По нему `pg_dump --snapshot` выгружает базу, и в
  той же транзакции читается список файлов. Документ, загруженный во время
  копирования, не попадёт ни в дамп, ни в список — рассогласования нет.
- **Пропавшие файлы.** Если файла документа на диске нет или его хэш не
  совпадает с именем, копия не падает: хэш уходит в `missing`, а интерфейс
  сообщает, сколько таких файлов. Отказ оставил бы организацию вообще без
  копий именно тогда, когда данные уже повреждены.
- **Незавершённый архив** пишется в `.part` и переименовывается только в
  конце.
- **Пароль к базе** передаётся `pg_dump`/`pg_restore` через `PGPASSWORD`, а
  не в командной строке: её видит любой процесс пользователя.
- **Не входят в копию:** модели и движок (скачиваются заново), пароли ролей
  PostgreSQL (у каждой установки свои, под DPAPI).
- **Шифрования нет.** Файл содержит все документы всех департаментов; об
  этом прямо сказано в интерфейсе. Шифрование паролем — возможное развитие.
- **Где работает.** Копию можно снять и со своей базы, и с внешнего сервера
  (`*_DATABASE_URL`) — через `pg_dump` из комплекта.

### Восстановление

Живые данные до перезапуска не трогаются.

1. **Проверка архива.** Формат, номер миграции не новее, чем знает эта
   сборка, имена файлов — только хэши. Дамп и каждый файл сверяются с описью
   по размеру и SHA-256 во время распаковки в `{app_data}/restore/`.
2. **Отдельная база.** Дамп разворачивается в `enclave_restore` рядом с
   живой: `pg_restore --no-owner --exit-on-error --single-transaction`.
   Владельцем объектов становится суперпользователь — как в базе, которую
   построили миграции. Права остаются: они выданы ролям приложения, а те
   есть в каждой базе Enclave.
3. **Миграции.** На `enclave_restore` накатываются миграции этой сборки.
   Старая копия доводится до текущей схемы сейчас, а не при запуске.
4. **Полнота.** У каждого живого документа есть файл — или он был в
   `missing` ещё в момент копирования.
5. **Метка.** Последним пишется `restore/staged.json`. До перезапуска
   восстановление можно отменить.

При запуске `EmbeddedPostgres::start`, ещё до подключения пулов, вызывает
`apply_staged`:

- `DROP DATABASE enclave`, затем `enclave_restore` переименовывается в
  `enclave`;
- каталог файлов заменяется новым;
- метка удаляется.

Каждый шаг можно повторить, поэтому запуск, прерванный на середине, доделает
подмену в следующий раз. Каталог `restore/` без метки — это брошенная
подготовка: его и `enclave_restore` запуск удаляет.

- **Аудит.** После подмены в журнал восстановленной базы пишется
  `backup_restored`: когда сделана копия и кто её подготовил. Подготовивший
  записан по имени, потому что его id был в заменённой базе. Снятие копии
  пишется как `backup_created`.
- **Внешний сервер восстановить нельзя.** Его базу используют и другие, а
  бэкапы сервера — забота его администратора и его средств. Команда
  отказывает с объяснением.

## Проверка

- **Тест `backup_roundtrip`.** Поднимает временный PostgreSQL из комплекта и
  проходит весь цикл:
  - снимает копию: два документа, файл одного уже потерян;
  - добавляет документ после неё;
  - пробует восстановить архив с одним испорченным байтом — получает отказ,
    не остаётся ни метки, ни `enclave_restore`;
  - готовит восстановление целой копии — живые данные не меняются;
  - делает подмену: документы, профили и файлы — как в момент копии, права
    `app_user` на месте, миграция последняя.

  Модульные тесты проверяют опись, отказ для копии из новой сборки и имена
  вида `../`. Тест пропускается там, где нет бинарников PostgreSQL (CI).
- **Docker-база** (PostgreSQL 16, 745 МБ, 50 027 фрагментов, миграция 15):
  - `pg_dump` 18 — 1,5 мин, дамп 192 МБ;
  - `pg_restore` в PostgreSQL 18 без единой ошибки, количество строк
    совпадает во всех проверенных таблицах.
- **В интерфейсе.** Копия с Docker-базы (5 документов, 194,5 МБ) восстановлена
  в установленном приложении. После перезапуска данные и вход работают.

**Время восстановления.** Почти всё время уходит на перестройку HNSW-индекса.

| `maintenance_work_mem` | Время |
|---|---|
| 64 МБ (по умолчанию) | 5,5 мин |
| 512 МБ | 2,9 мин |
| 1 ГБ, с параллельными воркерами | 2,9 мин |

`pg_restore` получает 512 МБ через `PGOPTIONS`. В Docker-базе HNSW-индекс
продублирован — наследие ручной сборки, — поэтому база из миграций
восстанавливается примерно вдвое быстрее.

## Последствия

- Копия доступна только администратору и содержит всё. Файл надо хранить
  так же бережно, как сам компьютер.
- После восстановления профили и PIN-коды — те, что были в копии.
- Копия, сделанная более новой сборкой, не восстанавливается: сначала нужно
  обновить приложение.
- Пока копия идёт, архив и временный дамп занимают место рядом с выбранным
  файлом. Пока идёт восстановление, данные занимают место дважды: живые и
  подготовленные.
- Расписания копий нет — только по кнопке.

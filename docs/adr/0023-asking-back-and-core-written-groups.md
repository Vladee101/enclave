# ADR-0023: Расчёт по угаданному столбцу — вопрос пользователю; список групп пишет ядро

- Статус: Принято
- Дата: 2026-09-25
- Решение принял: Vlad (Softwarean)
- Дополняет: ADR-0022

## Контекст

После ADR-0022 модель строит план расчёта в границах JSON-схемы. Ошибиться в
числах она не может, но может неверно понять вопрос. В интерфейсе это
проявилось сразу:

- «кол-во договоров и фамилия» модель разбила по «Контрагенту», хотя фамилии
  лежат в «Ответственном». В вопросе нет ни того, ни другого названия, и модель
  на 3B угадывает.
- «покажи количество договоров с фамилиями» — модель вообще отказалась
  считать.
- Даже при верном расчёте с разбивкой модель пересказывала список групп
  неверно: «Кол-во договоров: 50 000, фамилия: Иванов И.И.» при четырёх
  группах по 12 500. Список она склеивала, теряла числа или приписывала
  общий итог одному имени.

Подгонка промпта помогала одной формулировке и не помогала соседней.

## Решение

**1. Если план опирается на столбец, которого вопрос не называет, ядро
спрашивает пользователя.** Проверку делает ядро (`tables::plan::clarification`),
а не модель: модель на 3B не замечает, что сама угадала. Проверяются:

- **столбец разбивки**, кроме дат по периоду: у «по годам» одно прочтение;
- **столбец метрики** (sum / avg / min / max), если в таблице есть другие
  столбцы того же типа. «Самый ранний» при одном столбце дат однозначен.

Столбец считается названным, если его имя или одно из его значений
встречается в вопросе с поправкой на русские окончания: «статусу» называет
«Статус», «Иванова» называет «Ответственного», у которого есть значение
«Иванов И.И.». Основа слова — слово без двух последних букв, но не короче
четырёх. Этого хватает, чтобы отличить «фамилию» от «Контрагента», и это
детерминированно.

Вместо расчёта приходит вопрос («Уточните, по какому столбцу разбить
результат») и до пяти кнопок. Первая — выбор модели, дальше подходящие
столбцы и «Без разбивки». Каждая кнопка несёт **готовый план**. Нажатие
отправляет его вместе с исходным вопросом, и ядро выполняет этот план без
планировщика. План приходит от клиента, поэтому ему доверяют не больше, чем
выводу модели:

- таблица загружается по id **под RLS** (`load_candidate`), чужую таблицу не
  загрузить даже по её id;
- план проверяется тем же `parse_plan`;
- SQL собирается тем же компилятором из фиксированных фрагментов.

Уточнение пишется в журнал аудита: пользователю показаны только названия
столбцов, но вопрос касался этой таблицы.

**2. Если результат разбит на группы, текст ответа пишет ядро.** Ответ — это
сам список групп с числами, модель не вызывается. Пересказывать тут нечего, а
склеить список модель может. Одиночный результат («31 188 518 750», «10 000»)
модель по-прежнему пересказывает: с ним она справляется, и ответ звучит как
ответ, а не как отчёт. В интерфейсе готовый ответ приходит тем же событием
потока, одним куском.

## Проверка

На реестре из 50 000 строк, Qwen 2.5 3B:

| Вопрос | Было | Стало |
|---|---|---|
| кол-во договоров и фамилия | разбивка по «Контрагенту» | вопрос: Контрагент / Отдел / Статус / Ответственный / Без разбивки; «Ответственный» → 4 × 12 500 |
| У какого сотрудника больше всего договоров? | разбивка по «Ответственному», угадано | вопрос, первый вариант — «Ответственный» |
| количество договоров и фамилия ответственного | верно | верно, без вопроса («ответственного» называет столбец) |
| Сколько договоров по каждому статусу? | верно, но пересказ модели | верно, список пишет ядро |
| Сколько договоров по годам / самый ранний договор ИТ / общая сумма Петровой / 2021 год | верно | верно, без вопроса |

Тесты: `tables` — вопрос задаётся при неназванной разбивке и не задаётся при
названной (в том числе через значение столбца и через период даты); варианты
метрики только того же типа; каждый вариант разбирается обратно в план,
который обещает его подпись. `table_aggregation` — таблицу по id загружает
член департамента и не загружает чужой.

## Рассмотренные альтернативы

- **Дать модели третий исход («нужно уточнение»).** Модель, которая не
  заметила, что угадывает, не заметит и того, что пора спросить. Отклонено.
- **Продолжать подгонять промпт.** Каждая правка лечила одну формулировку.
  Отклонено как основной путь; примеры в промпте остаются.
- **Синонимы столбцов** («фамилия» → «Ответственный»). Словарь пришлось бы
  вести под каждую таблицу, а столбцы у каждой свои. Отклонено.
- **Модель на 7B для планировщика.** Может уменьшить число угадываний, но не
  отменит их, и занимает видеопамять. Остаётся на будущее; вопрос
  пользователю нужен при любой модели.
- **Писать ядром все ответы по расчётам.** Одиночный результат модель
  пересказывает верно, и ответ читается естественнее. Отклонено.

## Последствия

- Часть вопросов требует лишнего клика. «У какого сотрудника больше всего
  договоров» раньше отвечался сразу и верно, теперь сначала вопрос: слово
  «сотрудник» не называет столбец. Это цена детерминированной проверки:
  ядро спрашивает, когда план опирается на догадку, даже если догадка верная.
- Проверка не ловит лишние фильтры и неверную метрику (max вместо sum) — только
  выбор столбца. Для остального по-прежнему есть блок расчёта под ответом.
- Сгруппированный ответ не проходит через LoRA-адаптер департамента: голоса
  отдела в нём нет, есть только числа.
- `QueryArgs` получил поле `plan`, `QueryResult` — поле `clarification`.
  Выбранный план — вход от клиента под теми же проверками, что и вывод модели
  (инвариант №11 в CLAUDE.md).

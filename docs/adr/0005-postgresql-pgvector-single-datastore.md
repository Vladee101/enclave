# ADR-0005: PostgreSQL + pgvector как единое хранилище

- Статус: Принято
- Дата: 2026-06-29
- Решение принял: Vlad (Softwarean)

## Контекст

Системе нужны реляционные данные (пользователи, роли, департаменты, документы,
аудит) и поиск по векторному сходству над эмбеддингами. Это можно обслужить
одним движком или двумя специализированными. На машине пользователя каждый
лишний движок — ещё одна вещь, которую надо установить, бэкапить, защищать и
удерживать в согласованном состоянии.

## Решение

Использовать PostgreSQL с расширением pgvector для всего: реляционные таблицы,
векторный поиск и полнотекстовый поиск в одной базе.

## Рассмотренные альтернативы

- **Выделенная векторная БД (Qdrant, Weaviate, Milvus) рядом с Postgres** — две
  системы, которые надо развернуть и защитить on-prem, плюс согласованность
  между строками и их векторами через границу хранилищ. «У нас уже есть
  Postgres, мы не хотим ещё одно хранилище» — вдобавок реальный аргумент
  корпоративной закупки. Отклонено.
- **SQLite с векторным расширением** — легче и уже использовалось в прошлых
  проектах, но здесь подходит хуже: система опирается на Row-Level Security
  (ADR-0008) и зрелый ANN-индекс, а в Postgres сильнее и то, и другое.
  Отклонено.
- **In-process индекс вроде FAISS** — нет транзакционного хранилища и нет RLS,
  поэтому он не может быть системой записи. Отклонено.

## Последствия

**Плюсы**
- Один движок с транзакционной согласованностью между строками и их векторами.
- RLS одинаково накрывает и реляционные данные, и векторы.
- Меньше след на машине пользователя.

**Издержки**
- ANN в pgvector хорош, но на очень больших объёмах не самый быстрый вариант.
  Приемлемо: корпус одной организации ограничен.

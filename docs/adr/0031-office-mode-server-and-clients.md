# ADR-0031: Офисный режим — один сервер, клиенты без доступа к базе

- Статус: Предложено (уточняет ADR-0002, ADR-0014)
- Дата: 2026-10-04
- Решение принял: Vlad (Softwarean)

## Контекст

Сейчас Enclave — приложение одного ПК. На каждой установке своя база
(ADR-0014, PostgreSQL слушает только 127.0.0.1), свои файлы документов в
`{app_data}/blobs` (ADR-0013) и своя модель (ADR-0024, ADR-0025). Если
поставить его на три ПК в офисе, получатся три отдельные базы знаний. А
малому бизнесу нужна одна общая: юрист загрузил договор, менеджер по продажам
спрашивает о нём со своего ПК.

ADR-0002 с самого начала допускал локальную сеть («на машине пользователя или
в его локальной сети»), но как именно, не решал. Первое, что приходит в
голову, — подключить остальные ПК к базе первого через `*_DATABASE_URL`.
Технически это уже работает. Но тогда рушится модель безопасности.

- **Кто вы, решает клиент.** RLS (ADR-0008) доверяет пользователю, которого
  ядро записало в `app.current_user_id`. Сейчас это ядро на том же ПК, что и
  база, и по-другому до неё не добраться. Если положить пароль `app_user` на
  ПК сотрудника, он сможет достать пароль и подключиться к базе сам. Тогда
  одной командой `set_config('app.current_user_id', …)` он назовётся кем
  угодно и прочитает любой отдел. Пароли на ПК закрыты DPAPI, но DPAPI
  защищает от чужой учётной записи Windows, а не от владельца этой.
- **Роль обработчика загрузок обходит RLS** (инвариант 3). Каждый экземпляр
  запускает обработчик. Значит, пароль `ingest_worker` оказался бы на каждом ПК.
- **Файлы разъезжаются.** Файл ложится в `blobs` того ПК, где его загрузили.
  Задание забирает любой обработчик (`FOR UPDATE SKIP LOCKED`). Если это
  обработчик другого ПК, у него нет файла.

## Решение

**Три режима одной программы: «Один ПК» (как сейчас, по умолчанию),
«Сервер» и «Клиент».** Режим выбирается при установке и меняется в
настройках администратором.

### Что где живёт

| | Сервер | Клиент |
|---|---|---|
| PostgreSQL, пароли ролей | да, слушает только 127.0.0.1 | нет |
| Файлы документов | да | нет |
| Обработчик загрузок, OCR | да | нет |
| Модели и `llama-server` | да | нет |
| Резервные копии | да | нет |
| Интерфейс | да (сервер — тоже рабочее место) | да |

**Главный инвариант режима: на клиенте нет ни одного учётного данного базы.**
Клиент знает только адрес сервера, отпечаток его сертификата и после входа —
токен сессии. База наружу не открывается никогда: в сеть смотрит только
ядро сервера, и всё, что оно делает, идёт через те же команды и те же проверки,
что и сейчас.

### Транспорт

- **Ядро сервера отдаёт команды по HTTPS** — встроенный HTTP-сервер (`axum` +
  `rustls`), порт по умолчанию 47100, настраиваемый. Набор команд — тот же,
  что у Tauri (`cmd_*`). Команды уже тонкие обёртки над ядром, поэтому
  меняется транспорт, а не логика: одна функция ядра — два входа.
- **События** — потоковый ответ модели (`llm-token-*`), прогресс резервной
  копии и загрузки моделей — идут через SSE.
- **Интерфейс вызывает команды через одну функцию** (`call(cmd, args)`): в
  режимах «Один ПК» и «Сервер» это `invoke` Tauri, в режиме «Клиент» —
  `fetch` к серверу. Остальной интерфейс о режиме не знает.
- **Загрузка документа** уже передаёт байты файла в команду. В режиме клиента
  они уходят на сервер, а хеширование, запись файла и постановка задания
  происходят там. Ограничение размера — то же, что сейчас.

### Сессии и вход

- **Одна сессия на процесс заменяется сессиями по токенам.** `Session` сейчас
  хранит одного пользователя на процесс. На сервере каждая успешная проверка
  PIN выдаёт случайный токен (256 бит), и сервер держит в памяти
  `токен → пользователь`. Команда берёт пользователя из своего токена, никогда
  не из аргументов — как сейчас из `Session`.
- **Токен истекает** через 12 часов без активности, при выходе и при
  перезапуске сервера. После этого надо войти заново.
- **Окно самого сервера** работает как сейчас, через `invoke`, со своей
  сессией.
- **Подбор PIN по сети ограничен.** PIN короткий, а по сети попыток можно
  сделать сколько угодно. После 5 неудач для пользователя или для адреса
  следует пауза, которая растёт с каждой новой неудачей. Каждая неудача
  пишется в журнал аудита.
- **Администраторские команды** с клиента работают, проверка `is_admin` в базе
  на каждом вызове остаётся (`require_admin`).

### Подключение клиента к серверу

- **Сертификат.** При первом запуске в режиме сервера генерируется
  самоподписанный сертификат. Закрытый ключ хранится под DPAPI, как пароли ролей.
- **Код приглашения.** Администратор на сервере нажимает «Подключить
  компьютер» и получает одноразовый код: 16 символов base32 (80 бит), живёт
  10 минут, подходит для одного подключения.
- **Как проходит подключение.**
  - На клиенте вводится адрес сервера (имя компьютера или IP) и код.
  - Клиент получает сертификат сервера.
  - Сервер доказывает, что знает код: присылает HMAC от отпечатка своего
    сертификата, ключ HMAC — код.
  - Клиент проверяет HMAC и закрепляет отпечаток. Сервер отмечает код
    использованным.
  - Подменить сервер в сети без кода нельзя, а код живёт 10 минут и сгорает
    после первого подключения.
- **После этого клиент доверяет только этому отпечатку.** Сервер с другим
  сертификатом — ошибка `server_identity_changed`, не предупреждение, которое
  можно пропустить.
- Поиск сервера в сети (mDNS) отложен: адрес вводится руками один раз.

### Модель на несколько человек

- `llama-server` на сервере запускается с `--parallel 3` (число мест
  настраивается).
- `--ctx-size` делится между местами. Поэтому каждое место получает свои
  8192 токена: `--ctx-size 24576`.
- Кеш KV растёт пропорционально. Для Qwen3-4B в f16 это около 3,5 ГБ на три
  места. Если памяти мало, кеш квантуется в q8_0.
- Сервер эмбеддингов получает столько же мест.

### Версии и обновление

- При подключении и при входе клиент сверяет с сервером версию программы и
  последнюю миграцию. Нужно точное совпадение. Иначе ошибка
  `server_version_mismatch` с обеими версиями.
- Миграции запускает только сервер.
- Обновлять сначала сервер, потом клиентов.

### Установка

- Установщик спрашивает режим.
- Для сервера он добавляет правило брандмауэра Windows: входящие на порт
  ядра, только профиль «Частная сеть».
- Клиенту не нужны ни PostgreSQL, ни модели, ни движок. Пакет тот же, но при
  первом запуске клиент ничего не скачивает и базу не создаёт.

## Альтернативы

- **Подключать клиентов прямо к PostgreSQL** — личность задаёт клиент, а
  пароль `ingest_worker` лежит на каждом ПК (см. «Контекст»). Отклонено.
- **Своя роль PostgreSQL на каждого сотрудника, RLS по `current_user`.**
  Подделать личность стало бы нельзя. Но пришлось бы переписать все политики
  и обработчик загрузок, открыть PostgreSQL в сеть, а файлы и модель всё равно
  остались бы на одном ПК. Отклонено.
- **Веб-интерфейс в браузере вместо клиента.** Ставить на клиентские ПК было
  бы нечего. Но браузер покажет страшное предупреждение о самоподписанном
  сертификате, и закрепить отпечаток в нём нельзя. Сотрудников пришлось бы
  учить пропускать предупреждения безопасности. HTTP API тот же, так что это
  можно добавить потом, если у компании будет свой сертификат. Отложено.
- **Удалённый рабочий стол на один ПК.** В Windows Home нет сервера RDP, и
  одновременно работает один человек. Отклонено.
- **Модель на каждом клиенте, общие только база и файлы.** Снимает нагрузку с
  сервера, но каждому ПК нужны 3 ГБ моделей и железо под них, а вопрос личности
  всё равно решает сервер. Отложено как вариант для офисов с мощными ПК.
- **Общая папка Windows (SMB) для файлов документов.** Решает только
  разъезд файлов, не учётные данные. Отклонено.

## Проверка

- **Тест сессий по HTTP** — `rls_validation` через сервер:
  - Без токена — `not_signed_in`.
  - С токеном Bob — ни одного документа и ни одного чата Alice.
  - Подставить чужой `user_id` в аргументы нельзя: команда его не принимает.
  - Токен после выхода и после истечения срока не работает.
- **Подбор PIN:**
  - После 5 неудач — пауза, даже с верным PIN.
  - Неудачи видны в журнале аудита.
- **Подключение:**
  - Неверный код — отказ.
  - Использованный код — отказ.
  - Подменённый сертификат после подключения — `server_identity_changed`.
- **На клиенте нет учётных данных:** после подключения и работы в
  `{app_data}` клиента нет `db-secrets.bin`, `blobs`, `models`, `pgdata`.
- **Сквозная проверка на виртуалке** из ADR-0027 — она будет клиентом.
  Подключить её, загрузить документ с клиента, спросить о нём с сервера и
  наоборот. Три одновременных вопроса — замерить время ответа.

## Последствия

- Сервер должен быть включён и Enclave на нём запущен. Пока это обычное
  приложение, запущенное после входа в Windows (автозапуск и значок в трее).
  Запуск службой Windows без входа пользователя — отдельный шаг, позже.
- Безопасность всего офиса теперь равна безопасности ПК-сервера. Кто владеет
  его учётной записью Windows, владеет всеми данными — как сейчас у одного ПК.
- Режим «Один ПК» не меняется и остаётся по умолчанию.
- Резервная копия делается на сервере (ADR-0026), её карточка на клиенте
  скрыта.
- В сети появляется открытый порт. Это первый сетевой вход в Enclave, и его
  проверки — TLS, токены, ограничение попыток — теперь часть границы
  безопасности наравне с RLS.
- Статус «Предложено»: решение уточняется по ходу реализации. «Принято» —
  когда пройдёт проверка выше.

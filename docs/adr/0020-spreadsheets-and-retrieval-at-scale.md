# ADR-0020: Таблицы (XLSX, XLS, ODS) и поиск на их масштабе

- Статус: Принято
- Дата: 2026-09-24
- Решение принял: Vlad (Softwarean)

## Контекст

Значительная часть корпоративных знаний лежит в таблицах: реестры договоров,
прайс-листы, отчёты. ADR-0019 научил приём PDF и DOCX, таблицы отклонялись.

Таблицу нельзя превратить в текст так же, как документ. Выгрузка в духе CSV
оставляет заголовки столбцов только в первом фрагменте, и строка
«Иванов;Продажи;120000» в пятом фрагменте не значит ничего ни для поиска, ни
для модели. И таблицы большие: сквозной прогон на сгенерированном реестре из
50 000 строк × 8 столбцов показал три узких места, каждое из которых по
отдельности делало такой файл непригодным.

## Решение

**Строка — самостоятельная запись с заголовками:**

```
[лист «Зарплаты», строка 5] Имя: Иванов; Отдел: Продажи; Оклад: 120000; Дата приёма: 2021-03-15
```

Каждая строка несёт лист, номер строки как в Excel и заголовки столбцов,
поэтому любой фрагмент понятен сам по себе. Заголовки — первая из верхних
десяти строк, где не меньше двух заполненных ячеек и все они текст; строки над
ней (заголовок отчёта) сохраняются отдельными записями. Без такой строки
столбцы подписываются буквами. Значения: формулы — последним вычисленным
результатом, даты — `2021-03-15` (а не серийный номер Excel), целые числа —
без `.0`, `0.1 + 0.2` — как `0.3`, логические — «да» / «нет», пустые ячейки и
ошибки (`#N/A`, `#DIV/0!`) пропускаются.

**Чтение — `calamine`** (чистый Rust): XLSX, XLSM, XLSB, старый XLS, ODS.
Формат — по содержимому: ZIP с `xl/workbook.xml` — таблица, даже если файл
назван `.docx`; OLE-файл принимается как таблица только с расширением `.xls`
(`.doc` / `.ppt` — с подсказкой пересохранить).

**Нарезка по строкам:** фрагмент собирается из целых строк до 512 символов;
строка никогда не режется между фрагментами. Одна строка шире предела —
окнами фиксированной длины.

**Три узких места, найденные замером на 50 000 строках (RTX 4050), и их
решения:**

| | Было | Причина | Решение | Стало |
|---|---|---|---|---|
| Эмбеддинги | 49 текстов/с | один текст на HTTP-запрос | пакеты по 32 (`embed_batch`); 64 уже не быстрее | 148 текстов/с |
| | 95 текстов/с внутри приложения | llama-server пишет ~3 строки лога на текст, и каждая идёт через stdout-канал приложения | `--log-verbosity 1`: только ошибки (проверено: ошибка загрузки модели по-прежнему видна) | 146 текстов/с |
| Запись | ~11 мин | два SQL-запроса на фрагмент — 100 000 запросов | пакетная вставка: 1 000 строк на `INSERT … UNNEST`, векторы одним плоским массивом, нарезаемым в SQL | 3,9 мин; остаток — обслуживание HNSW (~3,7 мс на вектор, неустранимо при общем индексе) |
| Поиск | нужная строка 12 501-я из 50 000 | `ts_rank_cd` без IDF: «сумма», «договора» (в каждой строке) весят как «-012345» (в одной) | лексическая ветка с IDF: частота каждого слова вопроса считается под RLS (с потолком 1 000), кандидаты — только строки с редкими словами, ранг — сумма ln(1 + 1000 / df) | нужная строка в первой двойке |
| | 1,3–2,2 с | политики RLS вычислялись на каждой из 50 000 строк | ADR-0021 | 0,22 с |

Итог на 50 000 строках: приём 16,5 → **9,5 мин**, поиск 2,2 → **0,22 с**,
ответ модели на вопрос о конкретной строке — верный, с цитатой
(«Д-012345: сумма 2760055.5 руб., ответственный — Петрова А.С. [Source 2]»).

**Предел — 100 000 фрагментов на документ** (~100 000 строк таблицы, ~11 мин
эмбеддингов). Больше — ошибка задачи с советом разбить файл, а не час занятого
воркера и ~300 МБ векторов в памяти до записи (инвариант №4).

## Рассмотренные альтернативы

- **CSV-выгрузка листа.** Заголовки только в первом фрагменте. Отклонено.
- **Несколько строк в одном фрагменте** (~5 на 1 500 символов). Замер: скорость
  в строках почти та же (время GPU — на токены), базе в 5 раз меньше векторов,
  но вектор фрагмента размывается между пятью записями, и сервер эмбеддингов
  пришлось бы перенастроить под более длинные входы. Отклонено; вернуться,
  если объём базы станет проблемой.
- **Параллельные запросы к серверу эмбеддингов.** +20 % поверх пакетов ценой
  слотов и VRAM. Отклонено.
- **Удалить и перестроить HNSW при загрузке большого файла.** Индекс общий для
  всех департаментов; перестройка остановила бы поиск для всех. Отклонено.
- **Порог «слово встречается в > N % фрагментов»** вместо абсолютного
  потолка. На маленьком департаменте процент срабатывает на случайных словах;
  абсолютный потолок 1 000 ограничивает и стоимость подсчёта. Отклонено.

## Последствия

- **RAG отвечает на вопросы о конкретных строках, но не агрегирует.**
  «Сколько договоров исполнено в 2021 году» или «общая сумма по Петровой» не
  имеют ответа ни в одном фрагменте; модель увидит 5 строк и не должна делать
  вид, что посчитала. Для таких вопросов нужен другой механизм (запросы к
  таблице, text-to-SQL) — отдельное решение.
- **Объём:** ~12 КБ в базе на строку таблицы (текст, вектор, HNSW, GIN) —
  50 000 строк ≈ 700 МБ. После удаления большого документа место используется
  повторно, но не возвращается диску без `VACUUM FULL`.
- Ограничения разбора: многострочные и объединённые заголовки, заголовок-число
  (год) не распознаются как заголовки; проценты и валюта приходят хранимым
  значением (15 % → `0.15`); скрытые листы индексируются.
- Регрессия ловится тестами: таблица с заголовком отчёта, типами ячеек,
  листом без заголовков и пустым листом; нарезка по строкам;
  `tests/retrieval_ranking.rs` — 1 500 строк с общими словами и одна с нужным
  номером, под RLS, плюс чужой департамент. Без IDF тест падает (проверено).
- Инструменты: `cargo run --example extract_text -- <файл>` — что извлечётся и
  сколько фрагментов; `cargo run --example retrieve -- <пользователь>
  "<вопрос>" [--answer]` — что найдёт поиск приложения и что ответит модель.

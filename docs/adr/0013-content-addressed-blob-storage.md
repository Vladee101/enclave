# ADR-0013: Файлы документов хранятся по SHA-256 содержимого

- Статус: Принято
- Дата: 2026-09-29
- Решение принял: Vlad (Softwarean)

## Контекст

Исходный файл документа нужен после загрузки: воркер читает его позже
(ADR-0010), повторная обработка перечитывает, резервная копия (ADR-0026)
увозит. Хранить байты в PostgreSQL не хочется: файлы бывают по сотне
мегабайт, и база, дамп и `VACUUM` раздулись бы из-за данных, которые база
никогда не ищет. Значит, файлы лежат на диске, и нужно решить, как их
называть и когда удалять.

## Решение

**Файл лежит в `{app_data}/blobs/{sha256}`, где имя — SHA-256 его
содержимого в hex** (`commands/documents.rs`). В `documents` хранится
`file_hash`, пути нет.

- **Загрузка.** Хэш → запись файла → строка `documents` → задача.
  Файл пишется до вставки строки, поэтому воркер не увидит документ, байтов
  которого ещё нет на диске.
- **Дедупликация.** Уникальный индекс `(department_id, file_hash)` среди живых
  документов (миграция 009). Тот же файл в тот же отдел не создаёт второй
  документ: загрузка возвращает существующий, а упавший ставит в обработку
  заново — повторная загрузка и есть способ повторить. В разные отделы
  тот же файл загружается как разные документы, но **на диске он один**.
- **Удаление.** `delete_document()` и `delete_department()` сообщают, какие
  хэши больше не нужны ни одному живому документу ни в одном отделе
  (`blob_still_used`, `orphaned_blobs`). Файлы удаляются после фиксации
  транзакции и по возможности: не удалось — удаление документа всё равно
  состоялось.
- **Целостность.** Имя файла — его контрольная сумма. Резервная копия
  (ADR-0026) проверяет каждый файл по имени и перечисляет повреждённые и
  пропавшие.

## Альтернативы

- **Байты в базе (`bytea` или large objects).** Одна транзакция на всё и
  единый бэкап, но база растёт на объём файлов, а дамп и восстановление
  тянут их через SQL.
- **Путь по id документа.** Нет дедупликации, и имя ничего не говорит о
  содержимом: повреждение не обнаружить без отдельной суммы.

## Проверка

- `rls_validation`, раздел 7: удалённый документ сообщает свой файл как
  ненужный. Раздел 8: при удалении отдела файл, который использует живой
  документ другого отдела, в список на удаление не попадает.
- Резервная копия с потерянным и испорченным файлом: `backup_roundtrip` и
  модульные тесты `backup.rs`.

## Последствия и известные пределы

- **Осиротевшие файлы не собираются.** Файл остаётся без документа, если
  вставка строки не прошла после записи файла (отказ RLS, сбой) или его не
  удалось стереть после удаления документа. Они только занимают место:
  ничто их не читает, в резервную копию они не попадают. Сборщика мусора
  нет — он появится, если место станет проблемой.
- **Гонка удаления и загрузки того же файла.** Если последний документ с
  этим содержимым удаляют ровно в тот момент, когда те же байты загружают
  заново, файл может быть стёрт после записи новой загрузкой. Документ тогда
  упадёт при обработке с «не найден файл»; лечится повторной загрузкой.
  В однопользовательском настольном приложении окно почти недостижимо.
- **Чтение файла не сверяет хэш.** Воркер доверяет диску; сверка идёт только
  при резервном копировании.
- Файлы лежат на диске открытыми, как и `pgdata`: защита — учётная запись
  Windows и шифрование диска, а не приложение.
